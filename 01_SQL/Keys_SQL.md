# SQL Notebook: Understanding Keys in a Data Warehouse

## Why Do We Need Keys?

Keys uniquely identify records and define relationships between tables.

In a data warehouse, you'll commonly work with:

- Primary Keys
- Foreign Keys
- Business (Natural) Keys
- Surrogate Keys
- Composite Keys

Understanding the difference is essential for dimensional modeling.

---

# 1. Primary Key (PK)

A **Primary Key** uniquely identifies every row in a table.

Rules:

- Cannot contain duplicate values
- Cannot contain NULL values
- Only one PRIMARY KEY per table
- May consist of one column or multiple columns

Example

```sql
PRIMARY KEY (employee_key)
```

or

```sql
PRIMARY KEY (job_key, rfp_number)
```

### Purpose

- Enforces uniqueness
- Prevents duplicate records
- Identifies a single row

---

# 2. Composite Primary Key

A **Composite Primary Key** is a PRIMARY KEY made from multiple columns.

Example

```sql
PRIMARY KEY (job_key, rfp_number)
```

This means:

- A job can have many RFPs.
- An RFP number can repeat on different jobs.
- The combination must be unique.

Example

| job_key | rfp_number | Valid? |
|---------:|-----------:|--------|
| 101 | 5001 | ✔ |
| 101 | 5002 | ✔ |
| 102 | 5001 | ✔ |
| 101 | 5001 | ❌ Duplicate |

---

# 3. Foreign Key (FK)

A Foreign Key references another table.

Example

```text
dim_job
-------
job_key (PK)

fact_labor
----------
job_key (FK)
```

Purpose

- Creates relationships
- Maintains referential integrity
- Allows JOINs

For a Version 1.0 portfolio project, foreign key constraints are optional.

---

# 4. Business Key (Natural Key)

A Business Key is the identifier the business naturally uses.

Examples

| Business Object | Business Key |
|-----------------|--------------|
| Employee | Employee ID |
| Job | Job ID |
| Invoice | Invoice Number |
| RFP | Job ID + RFP Number |

Business keys come from the source system.

---

# 5. Surrogate Key

A Surrogate Key is an artificial key created by the database.

Example

```sql
employee_key INT AUTO_INCREMENT PRIMARY KEY
```

Characteristics

- Has no business meaning
- Never changes
- Used for joins in dimensional models

Example

| employee_key | employee_id |
|-------------:|-------------|
| 1 | EMP001 |
| 2 | EMP002 |
| 3 | EMP003 |

The business knows **employee_id**.

The warehouse uses **employee_key**.

---

# Business Key vs Primary Key

These are **not always the same thing**.

Example 1

```text
employee_key
employee_id
```

| Column | Type |
|---------|------|
| employee_key | Primary Key |
| employee_id | Business Key |

Different keys.

---

Example 2

```sql
PRIMARY KEY (job_key, rfp_number)
```

Here the Primary Key is built from the same columns that uniquely identify the business record.

In this case:

- Primary Key = Composite Key
- Primary Key also represents the business uniqueness rule.

---

# Which Key Am I Looking At?

Ask:

> **Who created this value?**

If the answer is:

"The business"

→ Business Key

Examples

- Job ID
- Invoice Number
- Employee ID

If the answer is:

"The database"

→ Surrogate Key

Examples

- employee_key
- job_key
- customer_key

---

# Example: dim_rfp

```sql
CREATE TABLE dim_rfp (
    job_key              INT,
    job_id               VARCHAR(10),
    rfp_number           INT,
    rfp_amount_invoiced  DECIMAL(12,2),
    date_job_complete    DATE,
    rfp_date             DATE,

    PRIMARY KEY (job_key, rfp_number)
);
```

### What do the keys mean?

| Column | Meaning |
|---------|---------|
| job_key | Surrogate key from dim_job |
| job_id | Business Job ID |
| rfp_number | Business RFP Number |

The table uses a **Composite Primary Key**:

```text
(job_key, rfp_number)
```

This enforces the grain:

> **One row = One RFP for one Job**

---

# Summary

| Key Type | Created By | Purpose |
|-----------|------------|---------|
| Primary Key | Database Designer | Uniquely identifies each row |
| Composite Key | Database Designer | Uniquely identifies a row using multiple columns |
| Foreign Key | Database Designer | Links tables together |
| Business Key | Business/System | Natural identifier used by the business |
| Surrogate Key | Database | Artificial identifier for warehouse relationships |

---

# Key Takeaways

- Every table should have a clearly defined grain.
- The PRIMARY KEY should support that grain.
- Business Keys come from the source data.
- Surrogate Keys are generated by the warehouse.
- Composite Primary Keys are perfectly valid when more than one column is needed to uniquely identify a row.
- In a dimensional model, surrogate keys are common for dimensions, but a Version 1.0 project can successfully use a composite primary key when it naturally represents the business grain.
